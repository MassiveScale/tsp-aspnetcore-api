# Output Cleaning

By default (`clean-output-dirs: true`) the emitter removes previously-generated
files from each output directory (models, interfaces, controllers, services,
helpers, and validators) **before** it writes new ones. This keeps the output in
sync with the spec: when you rename or delete a TypeSpec type, its old `.g.cs`
file is not left orphaned in the tree.

Cleaning only starts once every template, built-in or custom, has compiled. A
syntax error in a custom template reports `template-load-failed` and leaves
the existing output untouched.

## The cleanup manifest

Every run writes `.tsp-aspnetcore-api-manifest` to the emitter output
directory. It lists every file that run wrote, relative to that directory. On
the next run the emitter deletes exactly those files and nothing else. No
directory is scanned.

The manifest is JSON but has no `.json` extension. The .NET Web SDK copies
every `*.json` file in a project to the build and publish output, and the
manifest should not ship with your app.

Before deleting a listed file, the emitter checks that:

- it still lies inside one of the configured output directories,
- its name ends with `file-extension`, and
- it is a regular file reached without going through a symbolic link or junction.

An entry that fails any check is skipped, so a hand-edited or stale manifest
cannot delete anything outside the generated output. Because the manifest
identifies generated files by path, cleanup also works for output written by a
custom `file` template that has no emitter signature.

Commit the manifest alongside the generated code, or keep it wherever the
emitter output directory lives. If it is deleted, the next run falls back to
the signature scan described next.

## Signature scan (no manifest)

When no manifest exists yet (the first run, or after upgrading from
1.0.0-beta), the emitter scans each output directory recursively. A file is
deleted only when **both** conditions hold:

1. Its name ends with the configured `file-extension` (default `.g.cs`), and
2. One of its first 10 lines says it was generated by this emitter
   (`AUTO-GENERATED by @massivescale/tsp-aspnetcore-api`), or carries the
   exact header that 1.0.0-beta releases wrote.

A generic `<auto-generated>` marker is **not** enough. The .NET SDK
(`obj/*.GlobalUsings.g.cs`), EF Core (`*.Designer.cs`) and other code
generators write it too, so their files are always kept.

The scan never enters:

- `bin`, `obj` and `node_modules` folders,
- dot-folders such as `.git`, `.vs` and `.idea`,
- symbolic links or junctions, so it never leaves the output directory.

Anything else is preserved:

- A file that matches the extension but lacks the signature is **left in
  place** and reported with an `output-file-left-behind` warning naming the
  file, so you can decide whether to remove it yourself. When in doubt, the
  emitter keeps the file.
- Files that do not match the generated extension (e.g. hand-written `.cs`) are
  ignored silently.

Empty directories are left in place.

## Pointing an output directory at a project root

Cleanup is safe with an output directory such as `models-output-dir: "."` that
is also a C# project root. Build output, other generators' files and
hand-written code stay where they are. The emitter only removes files it wrote
itself.

## `file-extension`

`file-extension` must be one or more `.segment` parts made of letters, digits,
`_` or `-`, for example `.g.cs` or `.generated.cs`. An empty extension (which
would match every file), a bare `.`, or a value without the leading `.` is
rejected when the options are validated.

## Custom `file` templates

After the first run, the manifest identifies generated files, so a custom
`file` template needs no particular header. Keep the
`generated by @massivescale/tsp-aspnetcore-api` text within the first 10 lines
if you want the signature scan to recognise your files when no manifest exists
yet (see [Custom Templates](custom-templates.md)).

## Disabling

Set `clean-output-dirs: false` to disable cleanup entirely and only ever write
files. No manifest is written in that mode.
